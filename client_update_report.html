1. Executive Summary

This report responds directly to your technical questions and documents the work completed in this sprint. The short answers are: (1) we are using the native Gemini audio-to-audio Live API — not a cascaded STT→LLM→TTS pipeline; (2) playback was store-then-play in the previous build, and has now been replaced with a ring-buffer streaming approach; and (3) the ~7–8 s end-to-end latency we reported was caused by three specific buffering choices we have now removed — not by the relay or the Gemini model itself.

All three bottlenecks have been resolved in this sprint. A release APK has been built and is ready for on-device testing.

2. Your Questions — Direct Answers

Q1: Native audio-to-audio Live API, or cascaded STT → text Gemini → TTS?

Answer

We are using the native Gemini Multimodal Live API (audio-to-audio). The model is gemini-2.0-flash-live-001 over a persistent BidiGenerateContent WebSocket. PCM audio goes in at 16 kHz and PCM audio comes back at 24 kHz — no transcription, no text LLM call, no TTS step.

The latency table in the earlier report was misleading. Those figures (0.5 s STT + 4.0 s Gemini + 0.5 s TTS) were rough estimates written before the WiFi migration, when we were still discussing architectures. They do not describe the actual pipeline. We should have removed that table — apologies for the confusion. The 7–8 s figure we measured on device was caused entirely by three buffering decisions in our own code, not by model latency.

Q2: Playback — streamed per-chunk, or buffered until the full reply?

Answer

Previously: buffered (store-then-play). Now: ring-buffer streaming (play as decoded).

In the previous firmware, every Opus chunk was written to LittleFS flash and playback did not start until the app sent a DONE signal — meaning the toy was silent for the entire Gemini generation time before speaking a single word. This has been fully replaced in this sprint with a PSRAM ring-buffer approach: Opus packets are decoded to PCM the moment they arrive over TCP, written into a 512 ms PSRAM ring buffer, and the speaker starts playing after a 60 ms pre-roll (three decoded frames), while Gemini is still generating the rest of the response.

Q3: Where did the 4 seconds actually go? (Relay / buffering / cold starts)

Answer

There is no Cloud Run relay in the hot path. The mobile app connects directly to the Gemini Live API WebSocket. The only cloud function involved is a lightweight Supabase Edge Function (encode-opus) that converts PCM to Opus format — it is not in the round-trip audio path; it runs in parallel after Gemini responds. The 7–8 s breakdown was:

4. What We Tried — Direct PCM Streaming (and Why It Failed)

Before settling on the length-prefixed Opus packet approach, we attempted to stream raw PCM audio directly from the app to the ESP32 in real time as Gemini generated it. This would have been the simplest path, but it did not work reliably for the following reasons:

Why direct PCM streaming failed

1. No framing — TCP is a byte stream, not a packet protocol

TCP delivers a continuous stream of bytes with no inherent message boundaries. When we sent raw PCM without a length header, the firmware could not tell where one audio chunk ended and the next began. Chunks arrived merged, split, or partially — especially under WiFi congestion — producing corrupted audio with audible pops, skips, and glitches.

2. Nagle algorithm coalescing

Even with TCP_NODELAY set, the operating system and WiFi driver batched small writes together before transmitting. Two PCM chunks sent milliseconds apart would be delivered as a single TCP segment on the firmware side, and the firmware had no way to split them back correctly.

3. 24 kHz → 16 kHz downsampling artefacts mid-stream

Gemini returns audio at 24 kHz. We downsample to 16 kHz before the ESP32. When this conversion happened chunk-by-chunk without maintaining phase continuity between chunks, aliasing artefacts appeared at chunk boundaries — producing a distinctly distorted sound even when the bytes arrived in the correct order.

4. PSRAM bandwidth under concurrent WiFi + I2S DMA

Writing incoming PCM to PSRAM while I2S DMA was simultaneously reading from the same memory region caused bus contention on the ESP32-S3. At sustained 16 kHz stereo playback rates the DMA stalled intermittently, producing silence gaps.

Solution: Length-prefixed Opus packets

The approach we use now encodes PCM into Opus frames (320 samples / 20 ms) before sending. Each frame is prefixed with a 2-byte little-endian length: [uint16 len][opus bytes…]. This gives the firmware a clear framing boundary, so even if TCP splits a packet across two reads the firmware reassembles it correctly before decoding. Opus also compresses 16 kHz PCM by ~10×, reducing TCP transfer time, and the decoder handles the 24→16 kHz conversion as part of the encode step on the app side — so the firmware always receives 16 kHz-ready audio with no mid-stream resampling artefacts.

5. Latency Improvements Implemented This Sprint

Three changes were made targeting the three bottlenecks identified above:

Change 1 — Warm Gemini WebSocket session

File: src/services/GeminiLiveService.ts
Before: A new WebSocket was opened on every single turn — connecting, authenticating, and establishing the Gemini session. This cost ~500 ms per interaction.
After: The WebSocket session is opened once and kept open between turns. The turnComplete event no longer triggers a disconnect. Session reconnects only on explicit error or app backgrounding.

Change 2 — Parallel Opus encoding (pipeline overlap)

File: src/services/VoiceProcessingService.ts
Before: The app waited for Gemini to finish generating the entire response, then made a single HTTP call to the encode-opus Supabase function with all the PCM at once, then sent the result to the ESP32. These three steps were fully sequential.
After: As Gemini generates audio chunks, the app accumulates them into 1-second windows (32 640 bytes of PCM each). Each completed window immediately fires an encode-opus HTTP call that runs concurrently — while Gemini is still generating the next window. By the time Gemini finishes, most Opus chunks are already encoded. The app then streams them to the ESP32 in order as each encode promise resolves.

Change 3 — Firmware ring-buffer streaming playback

File: Arduino_code.md
Before: Incoming Opus chunks were written to LittleFS flash. Playback only began after the app sent a DONE:response.opus command, the file was closed, and the firmware opened it again for sequential reading. For a 5-second response this meant 5 seconds of silent waiting before the first word.
After:

  • Opus chunks are decoded to PCM immediately as they arrive over TCP
  • Decoded stereo PCM is written into a 512 ms PSRAM ring buffer (8 192 stereo sample pairs, 64 KB)
  • The I2S speaker task starts playing after a 60 ms pre-roll (3 decoded frames) — while the network is still receiving
  • The lullaby tune stops on first chunk arrival, giving way to the AI response seamlessly
  • The DONE signal now means "no more chunks coming" — not "start playing now"
  • A lock-free SPSC ring buffer (Core 0 writes, Core 1 reads) ensures no mutex overhead on the hot audio path

8. Known Limitations & Next Steps

API key security

Action required before production

The Gemini API key is currently embedded in the app bundle (src/config/voiceConfig.ts). This is acceptable for internal testing but must not be shipped to end users — the key is extractable from the APK. The recommended fix is to route Gemini calls through the existing Supabase edge function infrastructure so the key never leaves the server.

Arduino IDE compilation (ESP32 core version)

The firmware uses the legacy driver/i2s.h API. This requires the ESP32 Arduino core version 2.x (e.g. 2.0.17). The core 3.x series removed this header and renamed the API. When uploading firmware, ensure:

  • Board: ESP32S3 Dev Module
  • Core: esp32 by Espressif Systems v2.0.17 (not 3.x)
  • PSRAM: OPI PSRAM
  • Partition Scheme: Huge APP (3MB No OTA / 1MB SPIFFS)

Ring-buffer overflow on very long responses

The current ring buffer holds 512 ms of audio. If network jitter causes the TCP receive rate to fall significantly below the I2S playback rate, the buffer can underrun and produce a brief gap. This is unlikely on a local WiFi network but worth monitoring. Buffer size is a compile-time constant (STREAM_RING_STEREO 8192) and can be increased if PSRAM headroom allows.

Gemini model version

We are on gemini-2.0-flash-live-001. The gemini-live-2.5-flash model you mentioned (native audio output) targets lower TTFT and may further reduce first-audio latency. This is a one-line config change once the model is publicly available in the BidiGenerateContent endpoint.
